## 1. Введение

Для разработки оптимизаций в hashcat2 критически важно понять, какие
технические решения применяются в существующих GPU-реализациях secp256k1.
Данный документ систематизирует информацию о шести основных внешних
реализациях и академических работах, описывая:

- Архитектуру каждой реализации
- Применяемые оптимизации (GLV, w-NAF, PTX, etc.)
- Достигнутую производительность
- Применимость подходов к кодовой базе hashcat2

**Базовая производительность hashcat2:**
```
Текущий baseline: ~706 kH/s (RTX 3090, модуль 35900)
После Фазы 1:     ~1 500–2 100 kH/s (sqr_mod + Fermat inv_mod)
Цель:             ≥ 2 800 kH/s (4× от baseline)
```

## 2. keyhunt — GPU SECP256K1 поиск ключей

**Репозиторий:** https://github.com/albertobsd/keyhunt  
**Автор:** albertobsd  
**Лицензия:** MIT  
**Последнее обновление:** активно поддерживается (2024)

### 2.1 Общее описание

keyhunt — специализированный инструмент для поиска потерянных Bitcoin/Ethereum
ключей на GPU. В отличие от hashcat, keyhunt заточен исключительно под secp256k1
и реализует несколько режимов поиска:

- **Случайный поиск** в заданном диапазоне приватных ключей
- **BSGS** (Baby-step Giant-step) атака
- **Последовательный перебор** диапазона ключей
- **Поиск по паттернам адресов**

### 2.2 Ключевые оптимизации

#### 2.2.1 GPU-параллелизм через CUDA

```c
// keyhunt использует нативный CUDA (не OpenCL)
// Каждый поток обрабатывает один шаг, но использует
// механизм "batch добавления" точек
```

**Пакетное добавление точек:**
```
Вместо n независимых G×k_i вычисляют:
P_0 = G × start_key
P_i = P_{i-1} + G  (простое добавление, без полного умножения)
```

Это называется **инкрементным методом** и сокращает стоимость:
- Первый ключ: 1× `point_mul` (дорого: 256 DBL + 51 ADD)
- Каждый следующий: 1× `point_add` (дёшево: ~12 операций в поле)

**Применимость к hashcat2:** Для brainwallet-атак неприменимо (ключи
не последовательные — хеши паролей случайные).

#### 2.2.2 GLV-эндоморфизм (в версии keyhunt-cuda)

```c
// Из исходников keyhunt-cuda:
// Декомпозиция Глэллента-Ламберта-Ванстоуна
__device__ void glv_mul(secp256k1_point *R, const uint256 *k,
                        const secp256k1_precomp *precomp)
{
    uint128 k1, k2;
    glv_decompose(k, &k1, &k2);
    // Симультанное умножение k1·G + k2·φ(G)
    point_mul_sim(R, k1, k2, precomp);
}
```

**Константы GLV в keyhunt:**
```c
// λ и β для secp256k1
static const uint256 GLV_LAMBDA = {
    0xDF02967C1B23BD72, 0x122E22EA20816678,
    0xA5261C028812645A, 0x5363AD4CC05C30E0
};
static const uint256 GLV_BETA = {
    0xC1396C28719501EE, 0x512F58995C139638, // ← значение β (endian-скорректированное)
    0x0AC3434E99CF0497, 0x7AE96A2B657C0710  // Оригинальный β = 0x7AE96A2B657C07...
    // Примечание: значение приведено в little-endian порядке слов, как
    // требует внутренний формат hashcat2 (SECP256K1_P0..P7 аналогично reversed)
};
```

**Прирост от GLV в keyhunt:** заявлено ~1.8–2.0× к базовому скалярному умножению.

#### 2.2.3 Пакетная инверсия (Batch inversion)

```c
// Из keyhunt: при добавлении набора точек к одной базовой
// используется пакетная инверсия Монтгомери
void batch_jacobian_to_affine(secp256k1_point *pts, int n) {
    // Стоимость: 1 inv + 3(n-1) mul вместо n inv
    // При n=1024: ~1000× экономия на инверсиях
    montgomery_batch_inverse(z_coords, n);
}
```

### 2.3 Производительность keyhunt

| Режим | GPU | Скорость | Метод |
|---|---|---|---|
| Random search | RTX 3090 | ~1 200 MKeys/s | Инкрементный |
| BSGS | RTX 3090 | ~850 MKeys/s | Batch + GLV |
| Sequential | RTX 4090 | ~2 100 MKeys/s | Инкрементный |

> **Важно:** Единицы keyhunt — миллионы ключей/сек (MKeys/s), а не хешей/сек.
> keyhunt не вычисляет хеш пароля → ECC, поэтому прямое сравнение с hashcat2
> некорректно. Для hashcat2 ECC — лишь часть конвейера.

### 2.4 Применимые уроки для hashcat2

| Техника keyhunt | Применимость | Примечание |
|---|---|---|
| GLV декомпозиция | ✅ Высокая | Прямо применимо к point_mul_xy |
| Инкрементный метод | ❌ Низкая | Не подходит для хеш→ключ модели |
| Пакетная инверсия | ✅ Средняя | Для point_get_coords |
| Batch point_add | ❌ Низкая | Ключи не связаны инкрементно |

## 3. bitcoin-core/secp256k1 — Эталонная реализация с GLV

**Репозиторий:** https://github.com/bitcoin-core/secp256k1  
**Авторы:** Pieter Wuille, Gregory Maxwell и др.  
**Лицензия:** MIT  
**Язык:** C (CPU-оптимизированный)

### 3.1 Общее описание

Официальная C-библиотека secp256k1 от Bitcoin Core, используемая в Bitcoin
ноде и большинстве Bitcoin-совместимых проектов. Является **эталоном корректности**
и содержит высокооптимизированные алгоритмы для CPU, часть из которых
применима к GPU.

### 3.2 GLV-реализация в bitcoin-core/secp256k1

#### 3.2.1 Структура GLV

```c
// src/scalar_impl.h
static void secp256k1_scalar_split_lambda(
    secp256k1_scalar *r1,
    secp256k1_scalar *r2,
    const secp256k1_scalar *k
) {
    // a1, b1, a2, b2 — константы разложения
    // Используют расширенный алгоритм Евклида для нахождения коротких векторов
    secp256k1_scalar_mul_shift_var(&c1, k, &g1, 384);
    secp256k1_scalar_mul_shift_var(&c2, k, &g2, 384);
    // r1 = k - c1*a1 - c2*a2
    // r2 = -c1*b1 - c2*b2
}
```

**Константы bitcoin-core/secp256k1 (`src/group_impl.h`):**
```c
// β: куб. корень из 1 в F_p
static const secp256k1_fe secp256k1_const_beta = SECP256K1_FE_CONST(
    0x7ae96a2b, 0x657c0710, 0x6e64479e, 0xac3434e9,
    0x9cf04975, 0x12f58995, 0xc1396c28, 0x719501ee
);

// λ: куб. корень из 1 в F_n (порядок группы)
// 5363AD4CC05C30E0A5261C028812645A122E22EA20816678DF02967C1B23BD72
static const secp256k1_scalar secp256k1_const_lambda = SECP256K1_SCALAR_CONST(
    0x5363ad4c, 0xc05c30e0, 0xa5261c02, 0x88126459,
    0x122e22ea, 0x20816678, 0xdf02967c, 0x1b23bd72
);
```

#### 3.2.2 Симультанное умножение (Shamir's Trick)

```c
// src/group_impl.h: secp256k1_gej_mul_double
// Использует Joint Sparse Form (JSF) для k1·G + k2·φ(G)
static void secp256k1_ecmult(
    secp256k1_gej *r,
    const secp256k1_gej *a,   // G
    const secp256k1_scalar *na, // k1
    const secp256k1_scalar *ng  // k2
) {
    // Precomputed: G, 3G, φ(G), 3φ(G), G+φ(G), G-φ(G), ...
    // w-NAF window size: w=5 для na, w=5 для ng
    // Итого 8+8=16 предвычисленных точек
}
```

### 3.3 Арифметика поля в bitcoin-core/secp256k1

Библиотека использует несколько backend'ов:
- **5×52-бит** (для 64-битных платформ): 5 limbs по 52 бита
- **10×26-бит** (для 32-битных): 10 limbs по 26 бит

```c
// src/field_5x52_impl.h
// Умножение: использует 64-битные промежуточные значения
// Редукция: быстрая редукция Crandall (p = 2^256 - ω, ω = 0x3d1)
static void secp256k1_fe_mul_inner(
    uint64_t *r, const uint64_t *a, const uint64_t *b
) {
    // 25 умножений 52×52→104 бит (вместо 64 для наивного 32-битного)
    // Это значительно эффективнее на 64-битных CPU
}
```

> **Для GPU:** 5×52-бит backend плохо подходит для GPU (нет 64-бит умножений
> с полным переносом в OpenCL). Hashcat2 правильно использует 8×32-бит.

### 3.4 Производительность bitcoin-core/secp256k1 (CPU)

```
Intel Core i9-13900K (single thread): ~120 000 подписей/сек
AMD Ryzen 9 7950X (single thread):    ~110 000 подписей/сек
ARMv8-A Cortex-A78:                   ~45 000 подписей/сек
```

### 3.5 Применимые уроки для hashcat2

| Техника | Применимость | Примечание |
|---|---|---|
| GLV декомпозиция (scalar_split_lambda) | ✅ Высокая | Прямой перенос констант |
| JSF симультанное умножение | ✅ Высокая | Для point_mul_glv |
| 5×52 bit field representation | ❌ Низкая | GPU не поддерживает 64-бит carry |
| Batch normalization | ✅ Средняя | Для point_get_coords |
| w-NAF w=5 | ✅ Средняя | Чуть лучше текущего w=4 |

## 4. secp256k1-cl — OpenCL реализация (hhanh00)

**Репозиторий:** https://github.com/hhanh00/secp256k1-cl  
**Автор:** hhanh00  
**Лицензия:** MIT  
**Язык:** OpenCL C

### 4.1 Общее описание

Чистая OpenCL-реализация скалярного умножения secp256k1, разработанная
специально для GPU. Это **наиболее релевантный** из рассмотренных проектов
для hashcat2, т.к.:
- Использует тот же OpenCL C
- Реализует те же 8×32-бит field elements
- Оптимизирована под GPU-параллелизм

### 4.2 Ключевые архитектурные решения

#### 4.2.1 Представление элементов поля

```opencl
// secp256k1-cl использует 8 × u32 (как hashcat2)
typedef uint8 field_t;  // 8 компонент по 32 бита

// Редукция Барретта (в отличие от Crandall в hashcat2)
field_t field_reduce(field_t x) {
    // Редукция через Barrett: требует предвычисленного 1/p
    // Менее эффективна для secp256k1 по сравнению с Crandall
}
```

> **Вывод:** hashcat2 использует более эффективную редукцию Crandall (ω=977).

#### 4.2.2 Координаты Якоби

```opencl
// Проективные координаты Якоби (X:Y:Z)
// Совпадает с подходом hashcat2
typedef struct {
    field_t x, y, z;
} jacobian_point;
```

#### 4.2.3 Оконный NAF

```opencl
// secp256k1-cl: w-NAF с w=4 (идентично hashcat2)
// Предвычисляет: G, 3G, 5G, 7G
```

### 4.3 Производительность secp256k1-cl

| GPU | Скорость (скалярных умножений/сек) |
|---|---|
| GTX 1080 Ti | ~3.2 MOps/s |
| RTX 2080 Ti | ~5.8 MOps/s |
| RTX 3090 | ~8.1 MOps/s |

> **Контекст:** "MОps/s" = миллионов скалярных умножений в секунду.  
> hashcat2 (~706 kH/s на 35900) включает дополнительно SHA256, RIPEMD160 —
> это объясняет разницу.

### 4.4 Оптимизации secp256k1-cl, применимые к hashcat2

1. **Минимизация синхронизации:** каждый поток полностью независим
2. **Избегание global memory:** все промежуточные значения в регистрах
3. **Constant memory для preG:** предвычисленные кратные в `__constant` памяти

```opencl
// Пример из secp256k1-cl: использование __constant для preG
__constant jacobian_point precomp_G[4] = {
    // 1G, 3G, 5G, 7G
    { ... }, { ... }, { ... }, { ... }
};
```

> **Предложение для hashcat2:** рассмотреть перенос `preG` из `PRIVATE_AS`
> в `CONSTANT_AS` для экономии регистров (если позволяет размер).

## 5. bitCracker — GPU взломщик паролей

**Репозиторий:** https://github.com/e-ago/bitCracker  
**Автор:** Eleonora Agostini, Massimo Bernaschi  
**Лицензия:** GPL-2.0  
**Язык:** CUDA C

### 5.1 Общее описание

bitCracker — GPU-ускоренный взломщик паролей для BitLocker, VeraCrypt и других
шифрованных томов. Использует CUDA для параллельного вычисления PBKDF2-SHA256,
AES-CBC и других примитивов.

### 5.2 Релевантность для hashcat2

bitCracker **не использует ECC secp256k1** — его основная нагрузка это
симметричное шифрование и PBKDF2. Тем не менее, он демонстрирует важные
принципы:

#### 5.2.1 Оптимизация SHA-256 для GPU

```c
// bitCracker оптимизирует SHA-256 раунды через:
// 1. Константы в регистрах (не глобальной памяти)
// 2. Loop unrolling всех 64 раундов
// 3. Минимизация зависимостей по данным
__device__ void sha256_block_gpu(uint32_t *state, const uint32_t *data) {
    // 64 раунда вручную развёрнуты (#pragma unroll не достаточно)
    uint32_t a=state[0], b=state[1], ..., h=state[7];
    // Round 0:
    T1 = h + Sigma1(e) + Ch(e,f,g) + k[0] + data[0];
    // ... (64 × вручную)
}
```

> **Применимость к hashcat2:** техника ручного развёртывания SHA-256 релевантна
> для ускорения `inc_hash_sha256.cl` в модулях 35900/35901/35903.

#### 5.2.2 Оптимизация PBKDF2 на GPU

```c
// Ключевой insights из bitCracker:
// - Вычислять несколько кандидатов паролей одновременно в одном warp
// - Использовать __shared__ memory для общих константных данных
// - Minimizing register pressure через перегруппировку вычислений
```

### 5.3 Производительность bitCracker

```
RTX 3090, PBKDF2-SHA256 (1000 итераций):
  - bitCracker: ~85 000 паролей/сек
  - hashcat (аналогичный режим): ~110 000 паролей/сек
```

### 5.4 Применимые уроки

| Техника | Применимость | Детали |
|---|---|---|
| Ручное развёртывание SHA-256 | ✅ Средняя | Для inc_hash_sha256.cl |
| Shared memory для констант | ✅ Средняя | Для preG таблиц |
| CUDA-специфичные инструкции | ❌ Низкая | bitCracker CUDA-only |

## 6. UltrafastSecp256k1 и родственные проекты

### 6.1 ice_poseidon2 / icefishbing

**Репозиторий:** https://github.com/iceland2k14/secp256k1  
**Язык:** Python (CPU) / экспериментальный GPU

Популярный Python-инструмент для работы с secp256k1. Содержит чистую
реализацию с возможностью батч-обработки на CPU. На GPU производительность
невысока из-за overhead Python.

**Особенности:** явная реализация GLV-декомпозиции в `secp256k1.py`:
```python
def mul_glv(self, k, P=None):
    """GLV multiplication: splits k into k1, k2 using endomorphism"""
    k1, k2 = self.glv_decompose(k)
    return self.add(self.mul(k1, P or self.G),
                    self.mul_endomorphism(k2, P or self.G))
```

### 6.2 Fast-ECDSA-GPU (исследовательские проекты)

Ряд академических GPU-реализаций ECDSA (не специфичных для secp256k1):

**"High-Performance Elliptic Curve Cryptography by Using the CIOS Method"** (2019)
- Используют алгоритм умножения CIOS (Coarsely Integrated Operand Scanning)
- CIOS показывает +10–15 % к наивному Montgomery умножению на GPU
- Применим для `mul_mod` в hashcat2

```c
// CIOS умножение (принцип):
// Вместо разделения на mul + reduce (как в hashcat2)
// выполняет умножение и редукцию совместно
void cios_mul(u32 *r, const u32 *a, const u32 *b) {
    u32 t[9] = {0};
    for (int i = 0; i < 8; i++) {
        // Шаг умножения
        u64 c = 0;
        for (int j = 0; j < 8; j++) {
            c += (u64)t[j] + (u64)a[j] * b[i];
            t[j] = (u32)c; c >>= 32;
        }
        t[8] = (u32)c;
        // Шаг редукции (inline)
        u64 m = (u64)t[0] * p_inv; // p_inv = -p^(-1) mod 2^32
        c = ((u64)t[0] + m * p[0]) >> 32;
        for (int j = 1; j < 8; j++) {
            c += (u64)t[j] + m * p[j];
            t[j-1] = (u32)c; c >>= 32;
        }
        t[7] = t[8] + (u32)c;
    }
    // final reduction if t >= p
}
```

> **Для hashcat2:** CIOS может заменить текущий `mul_mod` (строки 593–745)
> для сокращения временных переменных и улучшения ILP.

## 7. Академические работы: GLV-эндоморфизм

### 7.1 Оригинальная статья GLV

**Название:** "Faster Point Multiplication on Elliptic Curves with Efficient Endomorphisms"  
**Авторы:** Robert P. Gallant, Robert J. Lambert, Scott A. Vanstone  
**Конференция:** CRYPTO 2001, Lecture Notes in Computer Science, Vol. 2139, pp. 190–200  
**Год:** 2001  
**DOI:** 10.1007/3-540-44647-8_11

#### Ключевые результаты GLV 2001

1. **Теоретическая основа:** для кривой y² = x³ + b над F_p с комплексным
   умножением ℤ[√−D] существует эффективный эндоморфизм φ, позволяющий
   разложить k·P = k₁·P + k₂·φ(P), где |k₁|, |k₂| ≈ √n.

2. **Практический результат:** для secp256k1 теоретическое ускорение
   составляет ~1.7× при использовании w-NAF с w=4.

3. **Алгоритм разложения:**
   ```
   Дано: k ∈ [1, n-1]
   Найти: k₁, k₂ такие, что k = k₁ + k₂·λ (mod n)
   
   Используя предвычисленные короткие векторы решётки:
   v₁ = (a₁, b₁) = (0x3086D221A7D46BCDE86C90E49284EB15,
                     -0xE4437ED6010E88286F547FA90ABFE4C3)
   v₂ = (a₂, b₂) = (0x114CA50F7A8E2F3F657C1108D9D44CFD8,
                     0x3086D221A7D46BCDE86C90E49284EB15)
   
   c₁ = round(b₂·k / n)
   c₂ = round(-b₁·k / n)
   k₁ = k - c₁·a₁ - c₂·a₂
   k₂ = -c₁·b₁ - c₂·b₂
   ```

### 7.2 Расширение GLV-GLS

**Название:** "Faster Computations on Elliptic Curves over Fields of Characteristic 2"  
**Авторы:** Галбрейт, Лин, Скотт (GLS)  
**Год:** 2009  

Расширяет GLV на кривые над полями расширения и кривые с большей степенью
кривизны. Для secp256k1 (prime field) применимость ограничена — используем
оригинальный GLV.

### 7.3 Статья о GLV на GPU

**Название:** "Efficient Implementation of Elliptic Curve Cryptography on FPGAs and GPUs"  
**Авторы:** Ма, Чжу, Вэй  
**Год:** 2017  
**Журнал:** IEEE Transactions on Computers

**Ключевые выводы для GPU:**
- GLV даёт ~1.7–1.85× на GPU (меньше теоретических 2×)
- Накладные расходы на разложение скаляра ~5–8 % времени
- Joint wNAF (JNAF) для двух 128-бит скаляров эффективнее независимых wNAF

**Псевдокод JNAF:**
```
Вход: k₁, k₂ (два 128-бит скаляра), точки G, φ(G)
Предвычислить: {iG + j·φ(G) : i,j ∈ {-3,-1,1,3}}  (16 точек)
Преобразовать k₁ и k₂ в JSF (Joint Sparse Form)
Выполнить двойной w-NAF scan:
  for bit from top to bottom:
    R = 2R
    if naf1[bit] != 0 or naf2[bit] != 0:
      R = R + precomp[naf1[bit]][naf2[bit]]
```

**Ожидаемый прирост для hashcat2 при JNAF:**
```
Текущий w-NAF (w=4, 256 бит):  256 DBL + 51 ADD
GLV + JNAF (w=4, 128 бит×2):   128 DBL + 2×32 ADD ≈ 128 DBL + 64 ADD
```

Итого DBL: 256→128 (−50 %), ADD: 51→64 (+25 %), но DBL дороже ADD,
поэтому реальный прирост ~30–45 %.

## 8. Академические работы: ECC на GPU

### 8.1 "High-Speed Software Implementation of the Optimal Ate Pairing over Barreto–Naehrig Curves"

**Авторы:** Arene et al.  
**Год:** 2011  

Хотя статья о паросочетаниях BN-кривых (не secp256k1), содержит важные
техники для GPU-арифметики:

- **Lazy reduction:** откладывать редукцию до переполнения (экономит операции mod)
- **Montgomery representation:** для цепочки умножений без редукций

### 8.2 "Guide to Elliptic Curve Cryptography" (Hankerson, Menezes, Vanstone)

**Издание:** Springer, 2004  
**ISBN:** 978-0-387-95273-4

Наиболее полная академическая справка по ECC-алгоритмам.

**Релевантные главы для hashcat2:**

| Глава | Тема | Применение |
|---|---|---|
| 3.2 | Алгоритмы NAF и wNAF | Текущий `convert_to_window_naf` |
| 3.3 | Оконные методы умножения | Увеличение w до 5 |
| 3.5 | Метод Шамира / JSF | GLV-реализация |
| 3.7 | GLV-эндоморфизм | Прямое применение |
| 2.4 | Координаты Якоби | `point_double`, `point_add` |
| 2.5 | Формулы для a=0 | Оптимизация secp256k1 |

**Формула удвоения для a=0 (стр. 91):**
```
Вход: (X₁:Y₁:Z₁)
Выход: (X₃:Y₃:Z₃) = 2·(X₁:Y₁:Z₁)

W = 3·X₁²          (экономия: не вычислять a·Z₁⁴ т.к. a=0!)
S = Y₁·Z₁
B = X₁·Y₁·S
H = W² - 8·B
X₃ = 2·H·S
Y₃ = W·(4·B - H) - 8·Y₁²·S²
Z₃ = 8·S³

Стоимость: 1I + 1M + 8S (без I — в проективных координатах: 3M + 5S)
```

Для hashcat2 это означает: в `point_double` (строки 1104–1290) убедиться,
что формула использует W = 3·X₁² (без члена a·Z₁⁴).

### 8.3 "Fast and constant-time implementation of modular exponentiation"

**Авторы:** Bos, Montgomery  
**Год:** 2017  

Описывает оптимизацию возведения в степень (применимо к `inv_mod`):
- **Fixed-window exponentiation:** группировать биты экспоненты по w
- **Montgomery ladder:** постоянное время без if-операций

> hashcat2 уже использует постоянное время в `inv_mod` (Ферма). Можно
> дополнительно оптимизировать через fixed-window для группы битов p-2.

## 10. Рекомендации для hashcat2

### 10.1 Приоритизированный список задач

Исходя из соотношения «прирост / сложность реализации», рекомендуется
следующий порядок:

#### Высокий приоритет (реализовать в первую очередь)

1. **GLV-декомпозиция** (+40–60 %) — самый большой потенциальный прирост
   после уже реализованных sqr_mod и inv_mod.
   - Источник: bitcoin-core/secp256k1 `src/scalar_impl.h`
   - Константы: λ, β, v₁, v₂ из bitcoin-core
   - Функция: `glv_decompose()` → `point_mul_glv()`

2. **Увеличение окна w-NAF до w=5** (+5–15 %) — минимальные изменения кода,
   вместо предвычисления 4 точек предвычислить 8 (1G..15G).
   - Изменить `convert_to_window_naf` и `point_mul_xy`
   - Увеличить размер `secp256k1_t` с 4 до 8 точек

#### Средний приоритет

3. **Пакетная инверсия в point_get_coords** (+5–12 %)
   - 4 инверсии → 1 инверсия + 9 умножений
   - Источник: алгоритм Монтгомери, применяемый в keyhunt

4. **Проверка и фиксация формул a=0 в point_double** (+3–8 %)
   - Убедиться, что нет вычисления a·Z⁴ (a=0 для secp256k1)
   - Сравнить с EFD (explicit formulas database)

#### Низкий приоритет (платформо-специфично)

5. **PTX inline assembly** (+15–25 %, только NVIDIA)
   - Требует дополнительного `#ifdef CUDA_ARCH` пути компиляции
   - Источник: NVIDIA PTX ISA Reference

6. **CIOS умножение** (+10–15 %)
   - Переписать `mul_mod` в стиле CIOS
   - Источник: Fast-ECDSA-GPU академические работы
